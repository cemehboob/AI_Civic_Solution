## 2. Project Background and Vision

We intend to develop a Voice-First E-Governance platform that enables rural and remote communities in Pakistan to access essential public services through natural spoken conversation.

The application should allow users to communicate with the system in their own language without requiring them to navigate menus, type text, understand complicated forms, or possess advanced smartphone skills.

The platform should act as a voice-based public service information and complaint assistance system.

The initial platform should focus on the following services:

1. Public complaint registration and complaint status inquiry.
2. Hospital, healthcare facility, doctor, and emergency service information.
3. Government subsidy, welfare scheme, and public assistance inquiries.
4. General public service information.
5. Guidance regarding government procedures, eligibility, documents, application steps, and relevant departments.

The platform should initially be designed as a pilot project for rural Pakistan, with the architecture allowing future expansion to additional districts, provinces, departments, services, and languages.

## 4. Core User Experience Principles

The application must be designed around the principle:

"Speak naturally, listen to the response, and complete the service without requiring reading, writing, or menu navigation."

The following UX principles are mandatory:

### 4.1 Voice-First Interaction

- The primary interaction method must be voice.
- Users should not need to type questions.
- Users should not be required to navigate traditional menus.
- The application must support spoken questions, follow-up questions, clarification, confirmation, and completion of tasks.
- The interface should provide a single prominent microphone interaction control.
- Users should be able to initiate and continue conversations naturally.
- The application should support conversational interaction rather than a rigid command-based system.

### 4.2 Minimal Visual Interface

Design the interface for users who cannot read or have limited literacy.

Use:

- Large icons.
- Large microphone controls.
- Visual status indicators.
- Simple illustrations.
- Audio instructions.
- Minimal text.
- Easy-to-understand confirmation indicators.
- Simple error recovery controls.
- Clear visual indication of listening, processing, and speaking states.

Avoid:

- Complex navigation.
- Long forms.
- Dense text.
- Technical terminology.
- Small buttons.
- Multiple layers of navigation.
- Interfaces that require users to understand application settings.

### 4.3 Conversational Interaction

The system must be capable of handling conversational examples such as:

- "Mujhe apne gaon ki sadak ke bare mein shikayat karni hai."
- "Mere qareeb koi sarkari hospital hai?"
- "BISP ki payment kab milegi?"
- "Meri pehli shikayat ka kya hua?"
- "Mujhe subsidy ke liye apply karna hai."
- "Punjab mein kis scheme ke tehat ghareeb logon ko madad milti hai?"

The system must understand conversational intent, context, incomplete statements, and follow-up questions.

The system should not force users to repeat all information during the same conversation.

## 6. Voice Interaction Workflow

Design a complete voice interaction workflow for both mobile and web applications.

The interaction should generally follow this sequence:

1. User opens the application.
2. The application presents a simple voice-enabled welcome experience.
3. The welcome message is played in the selected or detected language.
4. The user speaks.
5. Audio is captured through the device microphone.
6. Audio is processed using an appropriate ASR solution.
7. The recognized speech is converted into text internally.
8. The system identifies the user's language, intent, entities, and conversational context.
9. The system determines whether the request can be answered immediately or requires clarification.
10. The system retrieves relevant information from an appropriate verified data source, where required.
11. The LLM or conversational processing layer generates a response.
12. The response is converted into speech using the selected TTS engine.
13. The user hears the response.
14. The user can continue the conversation, ask a follow-up, correct information, or terminate the interaction.

The application must not expose the text-processing steps as a requirement for the user.

The user should experience the system as a natural spoken conversation.

### Conversation State

Design a conversation-state mechanism that maintains relevant context during the session.

For example:

User: "Mujhe hospital ka pata batao."

Assistant: "Aap kis ilaqay mein hospital dhoond rahe hain?"

User: "Rawalpindi ke qareeb."

Assistant: "Rawalpindi mein aap government hospital dhoond rahe hain ya koi bhi hospital?"

User: "Government hospital."

The system should retain the context without unnecessarily restarting the conversation.

Conversation history should be controlled, limited, and privacy-aware.

### Voice Interaction Modes

Evaluate and recommend:

- Push-to-talk.
- Automatic speech detection.
- Continuous conversational mode.
- Short audio recording mode.
- Streaming audio processing.

Recommend the most suitable approach for the MVP, considering battery usage, privacy, connectivity, low-end devices, and user experience.

## 11. Free LLM Routing and Model Switching Architecture

This section is mandatory and must be designed in detail.

The platform must never switch to a paid model when free model limits are exhausted.

### 11.1 OpenRouter Free Model Router

- OpenRouter's openrouter/free router automatically selects among eligible free models.
- It can fall back among eligible free models.
- It is not a guarantee of unlimited availability.
- Free models can have individual provider limits, availability limitations, and performance variation.
- If paid models are added to the fallback array, they may be billed.
- Accounts without any top-up history are limited to 50 requests per day for free models.
- After purchasing $10 in credits once, the free-model daily request limit increases to 1,000 requests per day, based on the stated verified information.
- Purchasing credits to increase the quota is not considered a requirement for this project, because the platform's operating principle is zero paid AI usage.

The system must not rely on an assumption of unlimited free OpenRouter inference.

## 21. Research and Recommendation Standards

- Verify the current status of relevant AI models.
- Verify Urdu and Punjabi support.
- Verify current model licensing.
- Verify free inference availability.
- Verify current provider restrictions.
- Verify OpenRouter free model routing behavior.
- Verify rate limits and quotas where publicly documented.
- Verify deployment requirements.
- Verify ONNX support.
- Verify CPU inference suitability.

- Verify relevant security and privacy considerations.

Prioritize:

1. Official documentation.
2. Official GitHub repositories.
3. Model cards.
4. Technical documentation.

- API limits.
